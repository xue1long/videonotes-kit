  一、build 硬约束（违反会导致 build 失败 / 步数统计错误）
  ------------------------------------------------------------
  1. 步骤标题必须写成 `### 步骤 N：标题`（H3，`步骤` 紧跟数字）。
     build 用 `^###\s*步骤` 计步数（consolidate.py:121），写成 `### A1：`、
     `### 第1步：` 都会被漏计，播放器/索引里的步数就少。
     👉 所以「路线」只能靠 H2 分组表达，**不能改步骤编号形式**。
  2. 图链在 _curated/<ep>/steps_pro.md 里必须写成 `](frames/frame_NNmSSs.png)`。
     build 用严格正则 `\]\(frames/(frame_(\d+)m(\d+)s\.png)\)` 匹配（consolidate.py:42）：
     文件名必须是 `frame_<分>m<两位秒>s.png`，不能写成 `./frames/`、`assets/`、或别的命名。
     匹配不到的图不会进 assets/，成品里就是死链。
  3. H1 与首个 H2 之间只放 1–3 行 `>` 元信息。
     build 会在「第一个 H2 之前」注入播放器入口条（consolidate.py:113），
     放多了会把 banner 挤到奇怪的位置。
  4. 「适用场景」等前置内容必须放在 H2 下，不要塞到 H1 与首个 H2 之间（同上）。

  ------------------------------------------------------------
  二、质量红线（人工/AI 精校时必须满足；可用 lint_p5.py 检查）
  ------------------------------------------------------------
  R1 覆盖完整：正文覆盖视频 0:00 到结尾。**禁止**出现「（后略，详见视频）」
     —— 这是 P4 时代最大的坑：polish 的 220 字截断会让后半集静默消失。
  R2 步骤 = 任务：一步 = 一个能独立完成的操作任务，不是「视频时间片」。
     禁止用分号把两件不相干的事缝进同一步。
  R3 标题 = 动作：动词开头 + 对象明确（「填入文案，挑音色」而非「大家打开剪映后」）。
  R4 每步必有自检：「**做对了的表现**：」，且必须可观察/可量化。
     纯判断步没有操作时，写「本步为判断步，无操作自检」。
  R5 图 = 操作时刻：截图取「操作发生那一刻」，不是时间片起点；
     图里必须能看到被操作的那个控件；与正文无关的画面一律不放。
  R6 caption 双写：`![步骤 N 截图 3m20s · 画面里该看什么](frames/frame_3m20s.png)`
     前段 `步骤 N 截图 xmxxs` 是可追溯锚点（体例要求），后段是这个画面要看的东西。
  R7 术语可搜索：所有软件名/按钮名必须能与真实界面或可搜索引擎对上。
     有把握不确定的，写「界面文字可能随版本变化，认功能不认名字」。
  R8 界面文字以截图为准：按钮名照抄画面（如「配音选择」≠「选配音声」）；
     字幕转述与画面冲突时，以画面为准并注明。
  R9 多路线必须显式互斥：出现 2 条以上「路线 X」时，路线总览下必须有一句
     「这些路线**互斥**，按你的情况选一条，不要顺序全做」。
  R10 颗粒度：单线集 6–8 步（上限 10）；多路线集每路线 3–5 步，总数 ≤ 12。
